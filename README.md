# Postcard Service

Команда: vlm: ВихляевМД, ГнеушевЛА, АндреевВВ

Серверный сервис (HTTP API), который превращает загруженную фотографию в готовую открытку. Клиент отправляет фото
и список операций оформления, сервис обрабатывает их в фоне и отдаёт результат в формате открытки.
Курс «Программная инженерия».

## Что умеет сервис: оформление открытки

Оформление задаётся списком операций в запросе. Операции применяются к одному изображению по порядку.
Каждая операция — отдельный Tool со своим набором параметров. Допустимы только перечисленные значения:
всё остальное сервис отклоняет с понятной ошибкой до начала обработки.

| Операция | Что делает | Параметры |
|---|---|---|
| `resize_crop` | Приводит фото к формату открытки. Ориентация (альбомная или книжная) выбирается по ориентации фото | `format`: `a6` (по умолчанию, 1748×1240 px) или `a5` (2480×1748 px); `fit`: `crop` (обрезка по центру, по умолчанию) или `pad` (фото целиком, белые поля) |
| `frame` | Добавляет рамку вокруг изображения | `style`: `thin` (тонкая линия) или `classic` (широкое белое поле, как у фотооткрытки); `width`: толщина в процентах от меньшей стороны, от 1 до 15 (по умолчанию 5); `color`: цвет в формате `#RRGGBB` (по умолчанию `#FFFFFF`) |
| `caption` | Добавляет подпись | `text`: до 100 символов (кириллица, латиница, цифры, знаки препинания); `position`: `bottom` (по умолчанию) или `top`; `add_city`: при `true` и наличии GPS в фото подпись начинается с «Привет из `<город>`». Если город определить не удалось, подпись формируется без него |
| `filter` | Меняет цветовое оформление | `name`: `sepia` или `grayscale` |
| `stamp` | Добавляет почтовую марку или штемпель | `style`: `stamp` (прямоугольная марка) или `postmark` (круглый штемпель с датой); `position`: `top_right` (по умолчанию), `top_left`, `bottom_right`, `bottom_left` |

Точные имена и ограничения параметров фиксируются в контракте OpenAPI (практика 2). Новая операция добавляется
как новый Tool без изменения ядра.

## Какую проблему решает

Сделать открытку из фотографии в графическом редакторе долго: нужно подобрать формат, рамку и подпись.
Сервис делает это за один запрос и в одном стиле. Он работает как фоновое задание: клиент загружает фото,
получает номер задания, затем проверяет статус и забирает готовый результат.

## Для кого

Сервис рассчитан на тех, кому нужно быстро получить аккуратную открытку из личной фотографии, но нет времени или навыков
для работы в графическом редакторе. Конечные пользователи получают открытки через приложения и чат-боты, построенные
на нашем API: пользовательский интерфейс в проект не входит (см. «Что точно не входит»).

| Группа | Что им нужно | Что для них важно | Как работают с сервисом |
|---|---|---|---|
| Путешественники | Отправить близким открытку со своей поездки | Подпись с названием места подставляется из GPS автоматически, результат выглядит как настоящая открытка | Через приложение или бот, который вызывает наше API |
| Те, кто поздравляет | Оформить личное фото к дню рождения, празднику, годовщине | Не нужно уметь пользоваться редактором: готовый результат за один запрос, единый стиль (рамка, штамп, подпись) | Так же, через приложение или бот |
| Разработчики небольших сервисов: поздравительные боты, фотостудии, магазины подарков, туристические приложения | Автоматически делать открытки для своих клиентов, не реализуя обработку изображений у себя | Чёткий контракт API (OpenAPI), понятные ошибки, повторный запрос не создаёт дубликат, обработка в фоне: можно отправить много заданий и забрать результаты позже | Напрямую по HTTP API |

## Что входит в систему

- Приём изображения и списка операций через HTTP API с машиночитаемым контрактом (OpenAPI).
- Асинхронная обработка: каждое обращение становится Job с жизненным циклом `created → running → done / failed / cancelled`.
- Набор операций (Tools) из раздела «Что умеет сервис». Новые операции добавляются без правки ядра.
- Подпись «Привет из `<город>`» по GPS из EXIF через внешний геокодер (адаптер с timeout, retry и fake для тестов).
- Хранение истории заданий в БД, файлов — в отдельном томе (см. «Где хранятся фотографии»).
- Автотесты: модульные, негативные, интеграционные. Запускаются одной командой и автоматически в CI на каждый PR.
- Структурированные логи, health check, запуск одной командой `docker compose up`.

## Где хранятся фотографии

Исходные фотографии и готовые открытки хранятся как файлы в отдельном томе (Docker volume), подключённом к сервису.
Сам контейнер файлы не хранит, поэтому при его пересоздании они не теряются. В базе данных лежат только данные
о задании (статус, параметры, время) и путь к файлам.

- **Структура:** `<id задания>/input.<расширение>` для исходника и `<id задания>/result.png` для результата.
- **Доступ:** только через API, файловая система наружу не открыта.
- **Срок хранения:** по умолчанию 7 суток после завершения задания, настраивается конфигурацией. После этого файлы
  удаляются, история задания остаётся в БД.
- **Внешнее хранилище:** S3-совместимое хранилище в первой версии не используется. Работа с файлами идёт через
  отдельный интерфейс хранилища, поэтому замена тома на S3 не затронет ядро.

## Что точно не входит

- Пользовательский интерфейс. Оформление выбирается параметрами запроса к API, а для проверки и демонстрации
  используется интерактивная документация API на основе OpenAPI (Swagger UI). Веб-страница поверх API возможна позже
  как необязательное дополнение и на ядро не влияет.
- Генерация и нейросетевая стилизация изображений: обработка детерминированная.
- Печать и физическая отправка открыток, платежи.
- Аккаунты, регистрация и авторизация пользователей.
- Ограничение частоты запросов и квоты (rate limiting) в первой версии.
- Долгое хранение фотографий: срок ограничен (см. «Где хранятся фотографии»).

## Как устроена система

```
запрос → Job → Dispatcher → Registry → Tool → ToolResult
```

Dispatcher берёт Job, по названию операции находит Tool в Registry и выполняет операции по порядку;
Dispatcher не знает конкретных Tool. Во втором семестре перед этой схемой встанет LLM, которая по фразе
на естественном языке составит список операций.
