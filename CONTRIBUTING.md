## 1. Управление задачами (Issue Management)

Все задачи, связанные с разработкой проекта, регистрируются в Issue Tracker репозитория.

Для классификации задач используются следующие Labels:

| Label | Назначение |
|---|---|
| `feature` | Разработка новой функциональности |
| `bug` | Исправление ошибок |
| `refactor` | Рефакторинг существующего кода |
| `documentation` | Работа с документацией |

Каждая задача должна содержать:

- Краткое и понятное название.
- Описание задачи и ожидаемого результата.
- Критерии приёмки (Acceptance Criteria), если применимо.
- Исполнителя (Assignee).

Перед началом работы разработчик назначает задачу на себя.

## 2. Git Workflow

В проекте используется упрощённая модель GitFlow.

### 2.1. Основные ветки

| Ветка | Назначение |
|---|---|
| `main` | Стабильная версия проекта, готовая к релизу |

Прямое внесение изменений в `main` запрещено. Все изменения должны проходить через Pull Request.

### 2.2. Ветки разработки

Для реализации задач создаются отдельные ветки от `main`.

**Формат названия ветки:**

```text
<issue-id>
```

Где:

- `issue-id` — идентификатор задачи в Issue Tracker.

### 2.3. Процесс слияния изменений

1. Разработчик создаёт ветку от `main`.
2. Выполняет необходимые изменения и фиксирует их коммитами.
3. После завершения работы создаёт Pull Request в `main`.
4. Pull Request проходит Code Review.
5. После одобрения и успешного прохождения автоматизированных проверок изменения объединяются с `main`.

Для слияния изменений используется **Squash Merge**.

## 3. Commit Convention

Для оформления сообщений коммитов используется стандарт [Conventional Commits](https://www.conventionalcommits.org/).

### 3.1. Формат коммита

```text
<type>: <description>
```

Где:

- `type` — тип изменения.
- `description` — краткое описание изменения.

Пример:

```text
feat: add JWT authentication
```

### 3.2. Типы коммитов

| Тип | Назначение |
|---|---|
| `feat` | Добавление новой функциональности |
| `fix` | Исправление ошибок |
| `docs` | Изменения документации |
| `style` | Изменения форматирования кода |
| `refactor` | Рефакторинг без изменения поведения |
| `test` | Добавление или изменение тестов |
| `chore` | Прочие технические изменения |
| `build` | Изменения системы сборки и зависимостей |
| `ci` | Изменения CI/CD |
| `perf` | Оптимизация производительности |
| `revert` | Отмена предыдущего коммита |

### 3.3. Правила оформления

- Сообщения коммитов пишутся на английском языке.
- Используется повелительная форма (например, `add`, `fix`, `update`).
- Описание должно отражать суть изменения.
- Коммит должен содержать логически связанные изменения.
- Не допускаются бессодержательные сообщения (`update`, `changes`, `fix bug`).

**Примеры:**

```text
feat: add JWT authentication
fix: prevent duplicate email registration
docs: update installation guide
refactor: simplify request validation
test: add login tests
chore: update dependencies
```

## 4. Code Review

Все изменения в основных ветках проекта проходят через Pull Request и Code Review.

### 4.1. Общие правила

- Автор Pull Request не может самостоятельно одобрить собственные изменения.
- Для принятия Pull Request требуется минимум одно одобрение другого участника команды.
- До слияния должны быть устранены все блокирующие замечания.
- После внесения исправлений Reviewer должен повторно проверить изменения.
- Pull Request должен быть связан с соответствующей задачей в Issue Tracker.

### 4.2. Критерии проверки

При проведении Code Review необходимо проверить:

1. Соответствие реализации требованиям задачи и критериям приёмки.
2. Соответствие принятым архитектурным решениям и структуре проекта.
3. Читаемость и поддерживаемость кода.
4. Отсутствие очевидных ошибок и проблем безопасности.
5. Отсутствие нежелательных изменений существующей функциональности.

### 4.3. Ответственность участников

**Автор Pull Request:**

- Предоставляет описание внесённых изменений.
- Отвечает на замечания Reviewer.
- Вносит необходимые исправления.

**Reviewer:**

- Проверяет изменения по установленным критериям.
- Оставляет замечания при обнаружении проблем.
- Одобряет изменения при отсутствии блокирующих замечаний.
- Мержит в таргет-ветку.

## 5. Definition of Done (DoD)

Задача считается выполненной, если соблюдены следующие условия:

1. Реализация соответствует требованиям задачи и критериям приёмки (Acceptance Criteria).
2. Код соответствует принятым в проекте стандартам разработки.
3. Изменения не нарушают существующую функциональность.
4. При необходимости обновлена техническая документация.
5. Pull Request успешно прошёл Code Review и получил необходимое одобрение.
6. Все блокирующие замечания Reviewer устранены.
7. Изменения успешно объединены с веткой `main`.
8. Соответствующая задача в Issue Tracker закрыта.
