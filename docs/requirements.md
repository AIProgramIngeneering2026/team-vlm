# Требования

## Сценарий 1. Создать открытку из фотографии (основной)

- **Цель:** получить готовую открытку из загруженной фотографии.
- **Участник:** клиент API.
- **Основной поток:**
  1. Клиент отправляет `POST /jobs` с изображением, списком операций (например, `resize_crop`, `frame`, `caption`) и заголовком `Idempotency-Key`.
  2. Сервис проверяет вход, создаёт Job в статусе `created` и отвечает `202` с `id` Job.
  3. Dispatcher берёт Job и переводит его в `running`.
  4. Для каждой операции Dispatcher получает Tool из Registry и выполняет их в заданном порядке.
  5. Если запрошена подпись с городом и в EXIF есть GPS, вызывается геокодер (см. сценарий 6).
  6. Результат сохраняется, Job переходит в `done`.
- **Критерии приёмки:**
  - **Дано** корректное JPEG/PNG в пределах лимитов и корректный список операций, **Когда** клиент отправляет `POST /jobs` с новым `Idempotency-Key`, **Тогда** сервис отвечает `202`, возвращает `id` и статус `created`, Job сохранён.
  - **Дано** Job в статусе `created`, **Когда** Dispatcher берёт его в работу, **Тогда** статус становится `running`, операции выполняются в порядке списка, каждая через Tool из Registry.
  - **Дано** все операции выполнены успешно, **Когда** результат записан в хранилище, **Тогда** Job переходит в `done`, а `GET /jobs/{id}/result` отдаёт открытку в формате PNG.

## Сценарий 2. Узнать статус и получить результат

- **Цель:** понять, готова ли открытка, и забрать её.
- **Участник:** клиент API.
- **Основной поток:**
  1. Клиент отправляет `GET /jobs/{id}`.
  2. Сервис возвращает статус и временные метки.
  3. Когда статус `done`, клиент отправляет `GET /jobs/{id}/result` и получает изображение.
- **Критерии приёмки:**
  - **Дано** существующий Job, **Когда** клиент запрашивает `GET /jobs/{id}`, **Тогда** сервис отвечает `200` с полями `id`, `status`, `created_at`, `updated_at`, а для `failed` ещё и `error` с кодом и сообщением.
  - **Дано** Job в статусе `done`, **Когда** клиент запрашивает `GET /jobs/{id}/result`, **Тогда** сервис отвечает `200` с `Content-Type: image/png`.
  - **Дано** Job в статусе `created` или `running`, **Когда** клиент запрашивает результат, **Тогда** сервис отвечает `409` с кодом `result_not_ready`.
  - **Дано** несуществующий `id`, **Когда** клиент запрашивает Job, **Тогда** сервис отвечает `404` с кодом `job_not_found`.

## Сценарий 3. Отменить задание

- **Цель:** остановить обработку, которая больше не нужна.
- **Участник:** клиент API.
- **Основной поток:**
  1. Клиент отправляет `POST /jobs/{id}/cancel`.
  2. Сервис проверяет, что отмена из текущего статуса разрешена.
  3. Job переходит в `cancelled`, выполнение прекращается, частичный результат не сохраняется.
- **Критерии приёмки:**
  - **Дано** Job в статусе `created` или `running`, **Когда** клиент отправляет `POST /jobs/{id}/cancel`, **Тогда** статус становится `cancelled`, а результат запросить нельзя (`result_not_ready`).
  - **Дано** Job в статусе `done`, `failed` или `cancelled`, **Когда** клиент отправляет отмену, **Тогда** сервис отвечает `409` с кодом `invalid_transition`, статус не меняется.

## Что предложил ИИ

**Модель:** Claude Sonnet 5.5

**Промпт:**

```
Вот основной сценарий сервиса: клиент загружает фото через POST /jobs с Idempotency-Key и списком операций;
сервис создаёт Job (created), Dispatcher переводит его в running, выполняет операции через Tools из Registry,
сохраняет результат и переводит Job в done. Статусы: created, running, done, failed, cancelled; отмена возможна из created и running.
Уже учтены сбои: битый файл, неизвестная операция, неверные параметры, двойная отправка с тем же ключом,
недоступность геокодера. Найди ещё 3 способа сломать этот сценарий, которых нет в списке.
Для каждого: что происходит, почему это ломает систему, как должна вести себя система.
```

**Предложения и решения:**

| # | Что предложил ИИ | Решение | Почему |
|---|---|---|---|
| 1 | Зависший Job: сервис перезапустился в момент `running`, и задание навсегда остаётся в этом статусе. | Принято | Реальная проблема. При старте сервис должен переводить «осиротевшие» `running`-Job в `failed` с кодом `interrupted`. Добавим как критерий и тест в задачу про жизненный цикл. |
| 2 | Гонка отмены и завершения: `cancel` приходит в тот же момент, когда Dispatcher переводит Job в `done`. | Принято | Переходы должны быть атомарными: побеждает тот, кто записан первым, проигравший получает `invalid_transition`. Результат отменённого Job не отдаётся. |
| 3 | Лавина заданий: клиент отправляет тысячи заданий подряд, очередь растёт, память и диск заканчиваются. | Отклонено для первой версии | Ограничение частоты и квоты вынесены за границы проекта (см. README, раздел «Что не входит»). Лимиты размера файла уже есть. Вернёмся к этому, если останется время. |
