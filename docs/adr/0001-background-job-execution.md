# ADR-0001. Фоновое выполнение Job в одном процессе с восстановлением при старте

- **Дата:** 2026-11-13
- **Статус:** принято

## Контекст и ограничения

Обработка одной открытки занимает от долей секунды до десятка секунд (подпись с городом ждёт внешний геокодер).
Клиент не должен держать соединение всё это время, а жизненный цикл Job (создан, выполняется, готов, ошибка, отмена)
должен быть виден через API. Ограничения курса: не больше трёх собственных сервисов, брокеры сообщений не оцениваются,

## Решение

Один сервис: HTTP API и Worker работают в одном процессе, Worker это пул потоков (по умолчанию 2).

1. `POST /jobs` записывает Job в БД со статусом `created`, кладёт его `id` в очередь в памяти и сразу отвечает `202`.
2. Если запись Job в БД успешна, но постановка его `id` в очередь завершается ошибкой, Job остаётся в статусе `created`.
Ошибка записывается в лог с `job_id` и `correlation_id`. Сервис не возвращает `202`; запрос завершается `503 service_unavailable`.
Запись Job при этом не удаляется. При следующем перезапуске сервиса Job со статусом `created` будет поставлен в очередь
механизмом восстановления, описанным в пункте 4.
3. Источник истины — БД. Worker берёт `id` из очереди и «захватывает» Job атомарным `UPDATE … SET status='running' WHERE id=? AND status='created'`;
   если строк не изменено, Job уже взят или отменён, и Worker его пропускает.
4. При старте сервис выполняет восстановление: все Job в `running` переводятся в `failed` с `error.code = interrupted`
   (их файлы удаляются), все Job в `created` заново ставятся в очередь.
5. Запуск допускается только в одном экземпляре.

## Рассмотренные альтернативы

- **Синхронная обработка в запросе.** Проще, но ломает модель Job, не позволяет отменять, упирается в таймауты клиентов
  и не оставляет места для статусов.
- **Отдельный сервис-обработчик с брокером (Celery и Redis или RabbitMQ).** Масштабируется, но добавляет сервисы и инфраструктуру,
  которые курс не оценивает, а команде пришлось бы настраивать и тестировать.
- **Отдельный процесс, опрашивающий БД.** Устойчивее к перезапуску API, но это второй запускаемый компонент без выгоды при текущей нагрузке.

## Цена решения

- Перезапуск обрывает выполняющиеся задания: клиент видит `failed` / `interrupted` и должен создать новое задание.
- Масштабирование по горизонтали невозможно: второй экземпляр при старте пометил бы чужие `running` как `interrupted`.
- Пропускная способность ограничена размером пула и памятью одного процесса.
- Очередь в памяти теряется при падении, но Job в `created` восстанавливаются из БД.

## Условия пересмотра

- Нужен второй экземпляр сервиса или нагрузка превышает возможности одного процесса: вынести Worker, заменить восстановление при старте
  на аренду задания (lease) с heartbeat.
- Операции станут долгими (минуты, например шаг с LLM во втором семестре): добавить повтор прерванных заданий.
